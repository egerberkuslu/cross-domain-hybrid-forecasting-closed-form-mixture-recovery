# Pre-registered repair rounds (release v2.1.0)

This folder holds the code, the registrations, the frozen parameter files and the result tables of the pre-registered repair rounds that the revised manuscript reports: the first two rounds (`paper_a/`, including `paper_a/round2/`) and rounds 3 to 7 (`round3/` to `round7/`). Round 5 is the fifth repair attempt of the accuracy claim (a quantile expert with a validation-chosen weight guard against Chronos-Bolt on fresh component series). Round 7 is the seventh registration of the monitor claim (a reference-free monitor on the error ratio of the two experts, on fresh CESNET subnet and address traces). Rounds 3, 4 and 6 are the earlier attempts that the text discloses. Release v2.0.0 does not contain any of this.

## Layout

```
repair_2026-10-12/
  README.md, verify_frozen.py
  paper_a/                 rounds 1 and 2: gate 0, a1 to a3, round2/ (gate E0, experts, a4, a5), rcommon.py, stats_tools.py,
                           REPAIR_PREREG.md, REPAIR_PREREG_2.md, frozen_a*.json/.sha256, RUN_NOTES.md, logs, result tables
  fresh_cells/             builders of the fresh component-series pools and their manifests (hashes of every series, no series values)
  round3/ ... round7/      per round: REPAIR_PREREG_n.md, PREREG_n_COMMITTED (and PREREG_n_SHA256 from round 6), RECIPE*_FROZEN.json,
                           frozen_r*.json/.sha256, stage scripts (r*_stages.py, r*_eval.py, r*_monitor.py), power calculations,
                           diagnosis notes (rounds 6 and 7), summary JSON, per-cell and per-run CSV tables, logs
```

The analysis scripts that turn these files into the numbers and tables of the manuscript are in `../../peerj_v2/scripts/` (`make_round5_numbers.py`, `make_round6_numbers.py`, `make_round7_numbers.py`, `make_repair_table.py`); their outputs are `../../peerj_v2/numbers_round{5,6,7}.{json,tex}` and `../../peerj_v2/tables/`. Run from the repository root, for example `python3 v2/peerj_v2/scripts/make_round7_numbers.py`; a rerun from the shipped files reproduces the shipped numbers and tables byte for byte.

## Frozen files are shipped byte for byte

The registrations record the SHA-256 of every code file of a round, and the run scripts refuse to start a test stage when a hash differs. The Python and shell files in this folder are therefore the files that ran, unmodified, including two things that look odd in a public repository: the shell scripts `run_r5.sh`, `run_r6.sh`, `run_r7.sh`, `download7.sh` name the author's workstation root as `ROOT=` (see *Running on another machine*), and the registrations refer to a coordinator role that commits a registration and writes its marker file. Only text logs and notes (`*.txt`, `*.md`) had the author's home directory replaced by `<REPO>`, `<CONDA>` or `<HOME>`.

```bash
python3 v2/experiments/repair_2026-10-12/verify_frozen.py
```

recomputes 125 digests (the code lists of every `RECIPE*_FROZEN.json`, every `frozen_*.sha256`, and `PREREG_6_SHA256`, `PREREG_7_SHA256`) and must print `125 digests match, 0 mismatch`. One file differs from its frozen digest by design: release v2.0.0 reworded two internal words in the docstring of `v2/experiments/fix_2026-10-11/monitor_far.py`; `verify_frozen.py` undoes exactly those two edits before hashing and reports a match.

The files `PREREG_n_COMMITTED` are the markers that open the test stage (`rcommon.allow_test()` refuses without them). They are shipped because they belong to the record; they carry the commit hash of the author's working repository in which each registration was committed before any test window was read (for example `b994136` for round 6). A rerun therefore starts with the test gate open, and the discipline of the original rounds (validation first, test only after a frozen selection) rests on following the order below.

## Running on another machine

The Python stage scripts locate everything from their own path. In this repository `v2/` plays the role of the author's workspace root, so the root must contain `data/`, `src/`, `outputs/` and the interpreter `.chas-venv/`. Link them once:

```bash
cd v2
ln -s ../data data && ln -s ../src src && ln -s ../outputs outputs && ln -s ../.venv .chas-venv
```

`../data/raw/{cesnet,abilene,geant}/` are the files the v1 loaders download (`python run_all.py --stage data`); `../outputs/` is the extracted v1.0.0 asset set (see `../README.md`); `.venv` is the environment of `requirements-lock.txt`. The shell drivers contain the workstation root, so run a rewritten copy placed outside the hash-checked folder (the originals stay unmodified and keep passing `verify_frozen.py`):

```bash
V2=$PWD   # inside v2/
for r in 5 6 7; do
  sed "s#/home/ege/Desktop/zaman-serisi-yayin#$V2#g; s#/home/ege/anaconda3#$(dirname $(dirname $(command -v python3)))#g" \
    experiments/repair_2026-10-12/round$r/run_r$r.sh > run_r$r.local.sh
done
```

This rewriting was checked for syntax (`bash -n`) and for leftover home paths; the full pipelines were not rerun for this release because they need the raw network traces and several hours of CPU.

## Commands per round

All commands run from `v2/` after the setup above, with `PY=.chas-venv/bin/python`, `R=experiments/repair_2026-10-12`, `export PYTHONDONTWRITEBYTECODE=1 OMP_NUM_THREADS=2`, and `nice -n 19 taskset -c 8-11` in front on a shared machine. Every round follows the same order: stage A (validation forecasts from train windows only), selection and freezing on validation arrays only, stage B (test forecasts after refitting on train and validation), test evaluation. Stage B and the test stages need `REPAIR_STAGE=test` and the `PREREG_n_COMMITTED` marker; stages A and the select stages must run without `REPAIR_STAGE`.

| Round | What it tests | Commands | Registered compute estimate (CPU, two workers) |
|---|---|---|---|
| 1 and 2 (`paper_a/`) | Gate 0 headroom, repaired weight rules (a1), alpha-monitor detectors (a2), learned alpha(x) (a3); round 2: complementary experts and their mixtures (gate E0, a5), drift-adaptive monitors (a4) | `python3 $R/paper_a/gate0.py`, `a1.py --stage select`, `a2.py --stage select`, `a3.py --stage select`; `REPAIR_STAGE=test python3 $R/paper_a/a2.py --stage test` (and `a3.py`, `a1.py --criterion floor`); round 2: `$R/paper_a/round2/gate_e0.py`, `a4.py`, `a5.py --stage select --experts EB EQ`, then the same with `REPAIR_STAGE=test` and `round2/experts_test.py` (GPU for Chronos-Bolt) | minutes per script, except the expert fits |
| 3 | E-Q against Chronos-Bolt on 20 fresh component series, reference-free monitor | `$PY $R/fresh_cells/build_pool.py`; `$PY $R/round3/r3_stages.py --stage A`; `$PY $R/round3/r3_eval.py --stage select`; `$PY $R/round3/r3_monitor.py --stage select`; then with `REPAIR_STAGE=test`: `r3_stages.py --stage B`, `r3_eval.py --stage test`, `r3_monitor.py --stage test` | 100 cells at 40 to 60 s (A) and 60 to 90 s (B), monitor selection about 20 min |

The main benchmark itself (all models, the nine traces and the seeds of the v1.0.0 release) takes about three hours on a single RTX 3060 GPU when re-derived from the raw inputs. Rounds 1 and 2 read its validation forecasts (`v2/experiments/fix_2026-10-11/val_forecasts/`) and, in their test stages, the v1.0.0 prediction assets; rounds 3 to 7 work on fresh component series built from the raw traces and need neither.

## Limits to know before citing

The sixth and seventh registrations were designed after earlier test outcomes were public, and the manuscript says so; the files here let a reader check the order of events, they do not remove that dependence. The fresh component series are not independent of the aggregate series of the main benchmark (same networks, same calendar periods). The series builder `fresh_cells/fresh_cells.py` flags values above 100 times the median of the whole series, which is not a train-only statistic; the registrations of rounds 5 and 7 state this limitation.
